Migrationen sind nach einem Teilfehlschlag nicht wiederholbar

Behoben Erledigt ArpaTools Kern Version 5.28.0 #515

Abgeschlossen am 09. August 2026

Eine Migration, die mitten im Skript scheitert, lässt die Datenbank in einem Zustand zurück, aus dem sie sich nicht mehr befreien kann. Jeder weitere Versuch scheitert erneut, und zwar an einer anderen Stelle als beim ersten Mal.

Der Ablauf. MigrationBase.RunMigration teilt das Skript an GO\r\n und schickt die Batches nacheinander an ExecuteNonQuery. Diese Methode wirft eine Ausnahme weiter (DbService.ExecuteNonQuery, catch (Exception) { throw; }). Scheitert also der dritte Batch, sind die ersten beiden bereits angewandt, die Ausnahme verlässt RunMigration, und die Versionsnummer in arpa.DbVersion wird nicht hochgesetzt. Das ist an sich richtig.

Beim nächsten Start liegt die Version weiterhin unter der Zielversion, die Migration läuft also erneut, diesmal aber gegen eine Datenbank, in der die ersten beiden Batches schon angewandt sind. Da die Skripte keine Existenzprüfungen enthalten, scheitert jetzt schon der erste Batch mit "There is already an object named ... in the database". Ab diesem Punkt kommt die Datenbank ohne Eingriff von Hand nicht mehr weiter, und die Ursache ist von der ursprünglichen Fehlerstelle verdeckt.

Beispiel. MigrationNetstockV10 besteht aus drei Batches: CREATE TABLE arpa.NetstockWarehouseSettings, ein INSERT zum Befüllen aus arpa.NetstockSettings.WarehouseIds, und ALTER TABLE arpa.NetstockSettings DROP COLUMN WarehouseIds. Scheitert der dritte, etwa weil eine Vorgabe- oder Indexabhängigkeit an der Spalte hängt, bleibt die Tabelle bestehen und jeder weitere Lauf scheitert am CREATE TABLE.

Vorschlag. Zwei Möglichkeiten, die sich ergänzen:

  1. Die Skripte idempotent schreiben, also IF OBJECT_ID(...) IS NULL vor CREATE TABLE, IF COL_LENGTH(...) IS NOT NULL vor DROP COLUMN und Entsprechendes. Das macht jeden Lauf wiederholbar, unabhängig davon, wie weit der vorherige kam. Vorbild ist MigrationSmartSupplyV9, dessen Test ausdrücklich die Idempotenz beim zweiten Lauf prüft.
  2. Die Batches einer Migration in einer Transaktion ausführen, damit ein Fehlschlag alles zurücknimmt. Das ist die gründlichere Lösung, aber nicht jede DDL-Anweisung ist in SQL Server sinnvoll transaktional, und der Umbau berührt alle bestehenden Migrationen.

Punkt 1 ist der kleinere Schritt und behebt den beschriebenen Fall vollständig.

Wie es aufgefallen ist. MigrationNetstockV10Tests.Run_CreatesTableAndDropsWarehouseIds_AndIsIdempotentOnSecondRun schlägt auf einer Entwicklungsmaschine fehl, an der Zusicherung, dass arpa.NetstockSettings.WarehouseIds nach der Migration verschwunden ist. Dort war die Migration einmal von Hand nachgeholt und die Version dabei auf 10 gesetzt worden, ohne die Spalte zu löschen. Die Versionsprüfung in MigrationBase.Run überspringt die Migration seitdem vollständig, das DROP COLUMN läuft nie, und der Test scheitert dauerhaft.

Dieser konkrete Fall ist ein Maschinenthema und kein Produktfehler. Er zeigt aber genau die Eigenschaft, um die es hier geht: sobald Versionsstand und tatsächlicher Schemazustand auseinanderlaufen, holt der Mechanismus das nicht mehr ein. Idempotente Skripte würden auch das auffangen.
