MigrationBase: Leer-Batch-Prüfung greift ins Leere

Behoben Erledigt ArpaTools Kern Version 5.28.0 #516

Abgeschlossen am 08. August 2026

In ArpaTools/Migrations/MigrationBase.cs, Methode RunMigration:

foreach (var sql in MigrationSql.Split("GO\r\n"))
{
    if (!string.IsNullOrWhiteSpace(MigrationSql))   // prüft das ganze Skript
    {
        databaseService.ExecuteNonQuery(sql, null, null, true);   // führt den einzelnen Batch aus
    }
}

Die Bedingung prüft MigrationSql, also das vollständige Skript, statt sql, den gerade abgespaltenen Batch. Da MigrationSql bei jeder Migration nicht leer ist, ist die Bedingung immer wahr und der Schutz gegen leere Batches greift nie.

Wirkung. Jedes Migrationsskript, das mit einer Leerzeile beginnt oder endet, oder das zwei GO hintereinander enthält, schickt einen leeren beziehungsweise reinen Kommentar-Batch an ExecuteNonQuery. Das ist heute folgenlos, weil SQL Server einen leeren Befehl toleriert, aber es ist erkennbar nicht die Absicht des Codes.

Beispiel: MigrationNetstockV10.MigrationSql beginnt mit einer Leerzeile und endet nach dem letzten GO mit einer weiteren, erzeugt also zwei solcher Batches.

Vorschlag. sql statt MigrationSql prüfen. Eine Zeile.

Warum es trotzdem gemeldet wird. Der Schutz existiert offensichtlich mit Absicht, er ist nur wirkungslos. Wenn ExecuteNonQuery später einmal strenger wird oder eine andere Datenbank angebunden wird, fällt es zur Laufzeit auf und niemand vermutet die Ursache in einer Bedingung, die seit Jahren danebengreift.

Gefunden beim Nachgehen eines fehlgeschlagenen Tests, siehe das verwandte Issue zur Wiederholbarkeit von Migrationen.

Automatisch aus dem Entwicklungs-Backlog erzeugt. Stand: 12. August 2026.
