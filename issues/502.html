Worker-Dienst arbeitet nach einem Server-Neustart nie wieder, meldet sich aber als laufend

Behoben Erledigt ArpaTools Kern Version 5.28.0 #502

Abgeschlossen am 07. August 2026

Gefunden beim Entwurf der Profilverwaltung (#57), nicht dort behoben.

Problem

ArpaToolsWorker/Worker.cs baut den WorkerService im Konstruktor und fängt die Exception nur weg:

public Worker()
{
    try { _workerService = new WorkerService(); ... }
    catch (Exception ex) { Log(ex); }
}

protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    if (_workerService == null) { Log("Worker Not Initialized"); return; }

Schlägt die Initialisierung fehl, ist _workerService null und ExecuteAsync steigt sofort aus. Danach tut der Dienst nie wieder etwas, meldet sich gegenüber Windows aber weiter als laufend. Es gibt keinen Retry.

Auslöser im Alltag

Der Konstruktor stellt über _configurationService.Init() (Services/WorkerService.cs:31) und die Lizenzprüfung schon eine Datenbankverbindung her. Nach einem Server-Neustart ist der Dienst mit start=auto oft früher bereit als SQL Server. Dann greift genau dieser Pfad.

Folge: keine Sammelrechnungen, keine Bestandssynchronisation, kein Retourenimport, bis jemand den Dienst von Hand neu startet. Auffällig wird das erst über fehlende Belege, weil die einzige Spur eine Zeile in %ProgramData%\arpaTools\ServiceLogs ist, die niemand proaktiv liest.

Erwartetes Verhalten

  • Die Initialisierung gehört nicht in den Konstruktor, sondern in ExecuteAsync, mit Wiederholung.
  • Scheitert sie, wird nach einem Backoff erneut versucht, statt endgültig aufzugeben.
  • Der Dienst darf sich nicht als betriebsbereit ausgeben, wenn er nichts tut.

Zusammenhang

Erklärt einen Teil des in #403 beschriebenen unzuverlässigen Verhaltens. Fällt strukturell weg, falls der Dienst im Rahmen des Multi-Profil-Umbaus die Arbeit an Kindprozesse abgibt, was dort aber ausdrücklich nicht vorgesehen ist.
